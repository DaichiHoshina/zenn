## この文、AI が書いたと分かりませんか

```markdown
本Design Docは、決済処理における一時的な障害(ネットワーク断、決済代行会社のタイムアウト、5xxエラーなど)で失敗した決済を、自動的にリトライする仕組みを導入するための設計方針を定めるものである。
```

間違ってはいないけど、**1 回読んだだけでは頭に入りません**。
後で紹介する実データの、AI が実際に書いた 1 文です。

AI に PR 本文や DesignDoc を書かせると、こういう文がよく入ります。
プロンプトで「こう書かないで」と頼んでも、しばらくすると元に戻ってしまう。

そこで、AI が書いた開発チームの文書を点検して書き換える、AI エージェント向けのスキル jp-lint を作りました！

https://github.com/DaichiHoshina/jp-lint

対象は、**開発チームの中で読み書きする文書** です。

- PRD
- DesignDoc
- PR 本文
- issue

## 想定する現場

- AI エージェントに PRD や DesignDoc、PR、issue を書かせている
- レビュアーが読んでも、何を決めたのか、何を変えたのかがすぐに分からない
- プロンプトで言い回しを指定しても、長い作業の途中で守られなくなる

## 書き直しのビフォーアフター

ここからは実際のデータです。

jp-lint を使わずに、Claude に DesignDoc を書かせました。
頼んだのは、決済の自動リトライ機能の「目的」「概要」「導入による効果」を、段落で書くことです。
ここでは「目的」と「概要」を載せます。

**Before (jp-lint なし)**

```markdown
## 目的

本Design Docは、決済処理における一時的な障害(ネットワーク断、決済代行会社のタイムアウト、5xxエラーなど)で失敗した決済を、自動的にリトライする仕組みを導入するための設計方針を定めるものである。現状、こうした失敗は利用者の再操作や運用担当者の手動対応に依存しており、売上機会の損失と運用負荷の増大を招いている。

## 概要

決済リクエストが失敗した際、エラー種別を「リトライ可能(一時的障害)」と「リトライ不可(カード残高不足、カード無効、不正判定など)」に分類し、リトライ可能なものだけを対象とする。リトライは指数バックオフ(例:1分、5分、30分)にジッターを加えた間隔で最大3回まで実行し、ジョブキューを用いた非同期処理として実装する。

二重課金を防ぐため、すべての決済リクエストに冪等キーを付与し、リトライ時も同一のキーを使用する。決済代行会社側の冪等性保証と自社DB上の状態管理(処理中・成功・失敗・リトライ待ち)を組み合わせ、状態遷移は楽観ロックで制御する。最終的に失敗した場合は、利用者へ通知を送り、運用向けのアラートを発報する。また、リトライ回数、成功率、遅延時間をメトリクスとして可視化し、障害時に即座にリトライを停止できるフィーチャーフラグを設ける。
```

これを jp-lint の script で検査した結果です (全文に対する結果)。

```text
[block] 比喩・擬人化 (block): 招い
[block] 構造: 連続漢字≥6: 2種 (決済代行会社 決済代行会社側) → 助詞挿入か訓読み開きで分ける
[warn] 構造: 読点≥4の文: 3個 → 文分割; 括弧詰め込み: 3件 (ネットワーク断、決済代行会社のタイムアウト、5x / カード残高不足、カード無効、不正判定など) → 括弧の名詞羅列を本文の文に開く; 同一文末3連続: 1箇所 (する×5) → 文をまとめるか 2 文目以降を下位 bullet に下げる
```

続けて、jp-lint のスキルだけを入れた Claude に書き換えさせました。

**After (jp-lint あり)**

```markdown
## 目的

本Design Docは、決済処理で一時的な障害により失敗した決済を、自動的にリトライする仕組みを導入するための設計方針を定めるものである。一時的な障害には、次のものがある。

- ネットワーク断
- 決済代行会社のタイムアウト
- 5xxエラー

現状、こうした失敗は利用者の再操作や運用担当者の手動対応に依存している。そのため、売上機会の損失と運用負荷の増大が生じている。

## 概要

決済リクエストが失敗したとき、エラー種別を次の2つに分類し、リトライ可能なものだけを対象とする。

- リトライ可能: 一時的障害
- リトライ不可: カード残高不足、カード無効、不正判定など

リトライとその周辺の仕組みは、次のとおりとする。

- リトライの間隔と回数
  - 指数バックオフにジッターを加えた間隔(例:1分、5分、30分)で、最大3回まで実行する
  - ジョブキューを用いた非同期処理として実装する
- 二重課金の防止
  - すべての決済リクエストに冪等キーを付与し、リトライ時も同一のキーを使用する
  - 決済代行会社が提供する冪等性保証と、自社DB上の状態管理(処理中・成功・失敗・リトライ待ち)を組み合わせる
  - 状態遷移は楽観ロックで制御する
- 最終的に失敗した場合
  - 利用者へ通知を送る
  - 運用向けのアラートを発報する
- 運用時の把握と停止
  - リトライ回数、成功率、遅延時間をメトリクスとして可視化する
  - 障害時に即座にリトライを停止できるフィーチャーフラグを設ける
```

主な書き換えは次のとおりです。

- 括弧に詰め込んでいた障害の種類とエラーの分類を、箇条書きに開いた
- 1 つの段落に詰め込んでいたリトライの仕組みを、「間隔と回数」「二重課金の防止」「最終的に失敗した場合」「運用時の把握と停止」の 4 つに分けた
- 「損失を招いている」を「損失が生じている」にした
- 「決済代行会社」は業務の用語なので、漢字の連続でも分けずに維持した

「導入による効果」の節では、「多くが自動的に回復し」のような言い切りを弱めました。
あわせて、効果が実測で確かめてあるなら事実に合わせて書き換えるよう、書き手に返しています。

**段落に詰め込まれた情報が箇条書きに分かれて、見出しと箇条書きを追うだけで構造がつかめる文書になりました**。
数値や根拠のように文書に無い事実は書き足さず、書き手への確認として返しています。

## 辞書で見つけて、モデルが判断する

jp-lint は、検査を 2 つに分けています。

| 担当 | やること |
|---|---|
| script | NG 語辞書と構造の検査で、気になる箇所を**見つける** |
| モデル | 前後の文を読んで、書き換えるか見送るかを**決め**、文を単位に書き換える |

辞書だけで置換すると、部分一致の誤検出で**意味が変わってしまいます**。
逆にモデルだけだと、見落としが毎回ばらつきます。

見つけるのは script、決めるのはモデル、と分けたのはこのためです。

:::message
検出された語だけを差し替えると、同じ問題が別の語の形で残ります。
書き換えは、検出された語を含む文を単位にします。
:::

モデルは、辞書では見つけられない型も点検します。

- 対処から始まる文 (「〜しているのは、〜だからです」)
- 参照先から離れた指示語 (「3 行目」「上の〜」)
- 記事や設計書など外向きの文章での、言い切った効果や根拠のない主張

## 辞書の中身

辞書は Markdown の 1 ファイルで、20 の分類があります。

| 分類の例 | 検出する語の例 |
|---|---|
| AI定型語 | を実現します、シームレスに、効果的に |
| 曖昧な汎用動詞 | を出す、を外す、を見る |
| 難読漢語 | 鑑みる、勘案、俯瞰 |
| 英語での業界用語 | fallback、canonical、trigger |

分類ごとに `block` (書き換える対象) と `warn` (文脈で判断する対象) を付けていて、**誤検出が多い語は warn に留めています**。

同梱の辞書は私が使っているものを元にしているので、人によっては合わない語もあるはずです。
`~/.config/jp-lint/ng-words.md` に追加したい語と除きたい語だけを記載すれば、**同梱の辞書を書き換えずにカスタマイズできます**。

```markdown
## 追加
**AI定型語**: させていただきます

## 除外
- canonical
```

## textlint との違い

日本語の文章 lint の代表例は textlint ですね。
ルールを組み合わせて、文の長さや表記の揺れを検出できます。

textlint にも `--fix` で自動修正する機能があります。
ただし、修正できるのは自動修正に対応したルールだけで、直し方もルールが決めた置き換えです。

jp-lint が違うのは、**検出した後の判断と書き換えまでをモデルに任せる**ところです。
前後の文を読んで書き換えるので、「影響なし」のような語にも、根拠を書き手に確かめる形で対応できます。

## 導入

リポジトリを clone して、同梱の `install.sh` を実行します。

```bash
git clone https://github.com/DaichiHoshina/jp-lint.git
cd jp-lint
scripts/install.sh               # Claude Code と、共通の置き場所を読む Cursor などへ配置
scripts/install.sh codex gemini  # エージェントを指定して配置
```

Agent Skills の形式 (`SKILL.md` を置いたフォルダ) に対応したエージェントなら、Claude Code 以外でも使えます。

bash 4 以上が必要です (連想配列を使っています)。

エージェントに「この文書を点検して」と頼めば動きます。

**これで準備は OK です！**

script だけ使うこともできます。

```bash
bash skills/jp-lint/scripts/jp-quality-lint.sh --strict 対象のファイル
```
