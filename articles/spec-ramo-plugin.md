## AI が書いた PR を、自分で説明できますか

> 「ここはなぜこうしたの？」

レビューでこう聞かれて、**自分の PR なのに即答できなかった**ことが多々ありました。

コードを書いたのは AI で、自分の理解は浅いままでした。

現場は**巨大なモノリス**のプロジェクト。
実装は速くなったのに、**開発全体はかえって遅く**、品質も低いまま。

体調まで崩して、さすがにまずい、と。

速く作れるようになったぶん、**「自分が理解しないまま進んでしまう」こと**がボトルネックになってました。

そこで、仕様駆動開発 (Spec-Driven Development、SDD) の手順を自分なりにまとめ、Spec Ramo (スペックラモ) というプラグインを作成しました！

https://github.com/DaichiHoshina/spec-ramo

## Spec Ramo とは

:::message
仕様を PR 単位の Phase に分けて、実装者が理解してから Phase を 1 つずつ進める、**仕様駆動開発の Claude Code プラグイン**です。
:::

名前は「スペック」と「クラモ」(サンスクリット語の krama＝「順序・段階」) を重ねた造語です。

想定しているのは、次のような現場です。

- **巨大なモノリスやマイクロサービス**のように、アーキテクチャが複雑
- 運用中のサービスで、既存コードの規約やアーキテクチャに合わせる必要がある
- サービスを止めずに、**既存の機能に影響を与えないようにリリースしたい**

困っていたことと、その対応が以下になります。

| 困りごと | Spec Ramo での対応 |
|---|---|
| PR が大きく、**読むのに時間がかかる** | 1 Phase = 1 PR にし、変更の上限 400 行 (テスト除く) をスクリプトで検査する (一般的にレビューしやすい行数を目安にしている) |
| 仕様で決めていなかった点に、**実装やレビューで気づく** | 実装の前に Design Doc で、見える動きを受け入れ条件の表に固定する |
| 実装者より先に、**レビュワーが問題に気づく** | 実装の前後に `/specramo:explain` で AI に説明してもらい、コードへの理解を深めて、問題点を事前に見つける |
| 規約や命名の指摘で、**レビューの往復が増える** | プロジェクトの規約の観点で AI がレビューし、規約や命名の指摘はレビュー依頼の前に解決しておく |

## 一般的な仕様駆動開発との違い

**仕様駆動開発は、コードより先に仕様を書いて、仕様を正として実装する手法です。**

代表例は GitHub の Spec Kit と AWS の Kiro ですね。

| 工程 | Spec Kit | Kiro | Spec Ramo |
|---|---|---|---|
| 要件を決める | specify | requirements | `/specramo:prd`・`/specramo:design` |
| 設計する | plan | design | `/specramo:design`・`/specramo:phase-design` |
| 作業に分ける | tasks | tasks | `/specramo:plan` |
| 実装する | implement | タスク実行 | `/specramo:implement` |
| 差を確認する | converge | なし | `/specramo:review` |
| 理解を確認する | なし | なし | `/specramo:explain` |

仕様と実装が合っているかを確認する仕組みは、既存の手法にもあります。

違いは最後の行、**実装者の理解を確認する工程**です。

## 使い方: PRD から PR まで

| 順番 | やること | コマンド | 詳細 |
|---|---|---|---|
| 1 | 準備 | `/specramo:init` | 設定ファイルと成果物の置き場所を作る |
| 2 | 要件 | `/specramo:prd` | 対話で要件を集めて PRD を作る |
| 3 | 設計 | `/specramo:design` | 受け入れ条件の表で振る舞いを固定した Design Doc を作る |
| 4 | 計画 | `/specramo:plan` | Design Doc を 1 Phase = 1 PR の作業計画書に分ける |
| 5 | 詳細設計 | `/specramo:phase-design` | Phase 1 つの実装方法を、既存コードを調べてから決める |
| 6 | 設計の説明 | `/specramo:explain` | 実装前に Phase の設計を説明する |
| 7 | 実装 | `/specramo:implement` | Phase を 1 つ実装し、完了条件をコマンドで確認する |
| 8 | レビュー | `/specramo:review` | 差分を 4 観点で並列にレビューする |
| 9 | コードの説明 | `/specramo:explain` | PR を draft で作ってから、差分のコードの説明と自分の認識を突き合わせる |
| - | 進み具合 | `/specramo:status` | Phase の進み具合と、この後に実行するコマンドを表示する |

1〜4 は最初に 1 回だけ、5〜9 は Phase ごとに繰り返します。

:::details 表にある文書の意味
- PRD: 何のために何を作るかをまとめた要件の文書
- Design Doc: 完成したときの振る舞いを決める設計書
- 受け入れ条件: 完成と言える条件。「〜のとき、〜が〜になる」の形で書く
- 作業計画書: Design Doc を Phase (= PR) に分け、Phase ごとの対象と完了条件を並べた文書
:::

### ゴールは「レビュー依頼のときに説明できる状態」

:::message alert
レビューを依頼するときには、PR の中身を自分の言葉で説明できる状態になっていることを目指します。
:::

レビューが終わったら PR を draft で作り、**AI によるコードの説明と自分の認識が一致したら**、draft を解除してレビューを依頼します。

PR を作る作業も含めて、手を動かす部分は AI に任せて構いません。
ただ、**レビュワーの前で中身を説明するのは、実装者自身**です。

## こだわったところ

### 1. 細かい決定ほど後で決める

文書は 3 種類あって、**細かい決定ほど着手の直前に決めます**。

| 文書 | 決めること | 作るタイミング |
|---|---|---|
| Design Doc | 何を作れば正解か (見える動き) | 最初に 1 回 |
| 作業計画書 | どの Phase で作るか | Design Doc の後 |
| Phase 詳細設計 | どう作るか (メソッド・SQL・トランザクション) | 各 Phase の着手直前。判断が無い Phase では省く |

着手する Phase の実装方法だけ読めば済むし、既存コードを調べてから決めるので、手戻りもぐっと減りました！

### 2. 後片づけの PR も最初に決める

後片づけも、作業計画書の段階で決めます。

既存の処理を置き換えるときは、切り替えの PR 群と、切り戻しの期間が過ぎてから古い処理を削除する PR 群に、最初から分けます。

**リリース後に不具合が見つかっても、切り替えだけを戻せるようにするためです。**

### 3. 実装の前と後で説明を変える

`/specramo:explain` は、実装前と実装後で説明する中身が変わります。

- 実装前: どの層にどの責務を置くか、なぜその設計にしたか、処理がどの順序で進むか
- 実装後: どの関数が何を受け取り何を返すか、テストが何を保証するか

説明の終わりには、**理解を確認する問いが 1〜5 個返ってきます。**

答えは折りたたんであるので、先に自分で考えてから開けます。
それを利用して、コード理解を深めます。

### 4. レビューは観点ごとに別の AI で

`/specramo:review` は、観点ごとに別のエージェントを並列で起動します。

| エージェント | 確認すること |
|---|---|
| 設計書との比較 | 作業計画書の範囲と受け入れ条件に沿っているか。対象外のファイルを変更していないか |
| 過去の指摘 | チームの過去のレビュー指摘の傾向と比べる (指摘データがあるときだけ) |
| リポジトリの規約 | リポジトリ独自の規約に沿っているか (規約があるときだけ) |
| 言語の指針 | 使っている言語の開発指針に沿っているか |

Critical と Warning が 0 件になってから PR を作るので、チーム固有の指摘も、人のレビューの前に見つけやすくなります！

## 導入

言語は問いません (同梱の言語指針は Go と TypeScript)。

Claude Code のセッションで、この 2 つを実行します。

```text
/plugin marketplace add DaichiHoshina/spec-ramo
/plugin install specramo@specramo
```

スコープ (user / project) を決めてインストールしたら、導入先のリポジトリで `/specramo:init` を実行します。

**これで準備は OK です！**

## 使ってみてどうだったか

数字では測ってないので、ここからは個人の体感です。

### ✅ 品質が上がった

理解してから PR を作るので、**レビューで初めて見つかる問題が減りました。**
レビューコメントの数そのものも少なくなり、付いたコメントへの返信や修正の時間も短くなりました！

### ✅ レビューの往復が減った

工程は 1 つ増えたけど、レビューの往復と手戻りが減ったぶんのほうが大きかったです。

### ✅ 頭の負担が減った

以前は何回も実装を出力し直していたけど、今は 1 回である程度理想のコードが出力できるので、**前みたいに毎日ぐったり疲れ切ることが減りました。**
(個人的にこれが一番うれしかったです！)

## おわりに

意外だったのは、**理解の工程を増やしたほうが速くなった**こと。

まさに急がば回れでした！

今は「ここはなぜこうしたの？」と聞かれたときに、**コードを調べ直す時間と返信までの時間が短くなりました。**

AI に任せる範囲が広がるほど、設計やコードを**自分がどれだけ速く理解できるか**が大事になると思ってます。

Spec Ramo はまだ試作の段階で、これからもブラッシュアップを続けます。

AI で実装は速くなったのに、レビューで止まってしまう人がいたら、ぜひ一度試してみて、ご意見をいただけるとうれしいです！
