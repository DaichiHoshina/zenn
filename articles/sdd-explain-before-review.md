## AI が書いた PR を、自分で説明できますか

> 「ここはなぜこうしたの？」

レビューでこう聞かれて、自分の PR なのに即答できないことが多々ありました。

コードを書いたのは Claude Code で、自分の理解は浅いままでした。
現場は巨大なモノリスのプロジェクトです。
実装は速くなったのに、開発全体はかえって遅く、品質も低いまま。

体調まで崩して、さすがにまずい、と。

速く作れるようになったぶん、**自分が理解しないまま進んでしまうこと**がボトルネックになってました。

この記事では、PR を出す前に AI にコードを説明させて、自分が理解してからレビューを依頼する進め方を紹介します。

## 進め方: 説明できるまで、レビューを依頼しない

:::message
仕様を PR 単位の Phase に分け、Phase ごとに **AI の説明と自分の理解が一致してから** レビューを依頼する進め方です。
:::

1 つの Phase の流れはこんな感じです。

| 順番 | やること | 誰が |
|---|---|---|
| 1 | Phase の実装方法を、既存コードを調べてから決める | AI |
| 2 | 実装の前に、設計を説明してもらう | AI |
| 3 | 説明を読んで、分からないところを聞き返す | 自分 |
| 4 | 実装して、完了条件をコマンドで確認する | AI |
| 5 | 差分を観点ごとにレビューする | AI |
| 6 | PR を draft で作り、コードを説明してもらう | AI |
| 7 | 説明と自分の認識が一致したら、draft を解除してレビューを依頼する | 自分 |

自分がやるのは、**説明を読んで、分からないところを聞き返す**ところです。
書く作業も PR を作る作業も、AI に任せています。

実際に自分がチャットで打っている言葉は、こんな感じです。
入力履歴から抜き出しました (コマンド名は、後で紹介するプラグインの形に揃えています)。

```text
/sdd:explain
/sdd:explain DB初心者向けに上記を説明
/sdd:explain 中学生向けで
/sdd:explain ジョインしたてエンジニア向け
/sdd:explain 指摘について説明して
/sdd:review 最後に全体みてほしい
/sdd:review 再度必要なルールを読み込んでレビュー
```

一度で分からなければ、「中学生向けで」のように読み手を変えて説明し直してもらいます。
分かったつもりで進むより、恥ずかしくても聞き返したほうが早いです。

## どこまで理解できたら依頼するか

基準はひとつで、**レビュワーの前で、中身を自分の言葉で説明できるか**です。

説明の終わりには、理解を確認する問いが 1〜5 個返ってきます。
答えは折りたたんであるので、先に自分で考えてから開けます。

答えられなかった問いがあれば、そこが自分の理解の足りないところです。
その箇所をもう一度説明してもらってから、レビューを依頼します。

## ビフォーアフター

| | 以前 | 今 |
|---|---|---|
| PR の大きさ | 大きく、読むのに時間がかかる | 1 Phase = 1 PR で、変更は 400 行まで (テストを除く) |
| 仕様の抜け | 実装やレビューで初めて気づく | 実装の前に、見える動きを受け入れ条件の表に固定する |
| 問題に気づく人 | 実装者より先にレビュワーが気づく | 実装の前後で説明を受け、自分が先に気づく |
| 規約や命名の指摘 | レビューの往復で修正する | レビュー依頼の前に AI のレビューで解決する |
| 「なぜこうしたの？」 | コードを調べ直してから返信する | 調べ直す時間と返信までの時間が短くなった |

工程は増えました。
それでも、レビューの往復とやり直しが減ったぶんのほうが大きかったです。

## こだわったところ

### 1. 実装の前と後で、説明の中身を変える

実装前と実装後では、知りたいことが違います。

| タイミング | 説明してもらうこと |
|---|---|
| 実装前 | どの層にどの責務を置くか、なぜその設計にしたか、処理がどの順序で進むか |
| 実装後 | どの関数が何を受け取り何を返すか、テストが何を保証するか |

実装前に設計を理解しておくと、実装後の説明もすっと入ってきます。

### 2. 細かい決定ほど後で決める

最初に細部まで決めると、前の Phase の実装で前提が変わって、設計を作り直すことになります。
なので、文書を 3 種類に分けて、**細かい決定ほど着手の直前に決めます**。

| 文書 | 決めること | 作るタイミング |
|---|---|---|
| Design Doc | 何を作れば正解か (見える動き) | 最初に 1 回 |
| 作業計画書 | どの Phase で作るか | Design Doc の後 |
| Phase 詳細設計 | どう作るか (メソッド・SQL・トランザクション) | 各 Phase の着手直前 |

着手する Phase の実装方法だけ読めば済むので、説明を受けるときの負担も小さくなります。

### 3. 後片づけの PR も最初に決める

リリース後に不具合が見つかっても、切り替えだけを戻せるようにしたいです。

そのために、既存の処理を置き換えるときは、切り替えの PR 群と、古い処理を削除する PR 群を最初から分けます。
削除の PR は、切り戻しの期間が過ぎてから出します。

### 4. レビューは観点ごとに別のサブエージェントで

規約違反や見落としは、人のレビューの前に見つけておきたいです。
なので、観点ごとに別のサブエージェント (Claude Code の中で並列に動く別の AI) にレビューさせています。

| 観点 | 確認すること |
|---|---|
| 設計書との比較 | 作業計画書の範囲と受け入れ条件に沿っているか |
| 過去の指摘 | チームの過去のレビュー指摘の傾向と比べる |
| リポジトリの規約 | リポジトリ独自の規約に沿っているか |
| 言語の指針 | 使っている言語の開発指針に沿っているか |

指摘は重さで Critical と Warning に分かれていて、どちらも 0 件になってから PR を作ります。

## 自分の現場で試すなら

この進め方のコマンドは、sdd というプラグインにまとめて、自作のプラグインの配布元 daidai で公開しています。

https://github.com/DaichiHoshina/daidai

Claude Code で次の 2 行を実行すると入ります。

```text
/plugin marketplace add DaichiHoshina/daidai
/plugin install sdd@daidai
```

インストールしたら、導入先のリポジトリで `/sdd:init` を実行すれば準備は OK です。
言語は問いません (同梱の言語の指針は Go と TypeScript)。

:::details sdd のコマンドの一覧
| 順番 | コマンド | やること |
|---|---|---|
| 1 | `/sdd:init` | 設定ファイルと成果物の置き場所を作る |
| 2 | `/sdd:prd` | 対話で要件を集めて PRD (何のために何を作るかの文書) を作る |
| 3 | `/sdd:design` | 受け入れ条件の表で振る舞いを固定した Design Doc を作る |
| 4 | `/sdd:plan` | Design Doc を 1 Phase = 1 PR の作業計画書に分ける |
| 5 | `/sdd:phase-design` | Phase 1 つの実装方法を、既存コードを調べてから決める |
| 6 | `/sdd:explain` | 実装前は設計を、実装後は差分のコードを説明する |
| 7 | `/sdd:implement` | Phase を 1 つ実装し、完了条件をコマンドで確認する |
| 8 | `/sdd:review` | 差分を観点ごとに並列でレビューする |
| - | `/sdd:status` | Phase の進み具合と、この後に実行するコマンドを表示する |

1〜4 は最初に 1 回だけ、5〜8 は Phase ごとに繰り返します。
:::

## 使ってみてどうだったか

数字では測ってないので、ここからは個人の体感です。

### ✅ レビューで初めて見つかる問題が減った

理解してから PR を作るので、**レビューで初めて見つかる問題が減りました。**
レビューコメントの数も少なくなり、返信や修正の時間も短くなりました！

### ✅ 頭の負担が減った

以前は何回も実装を出力し直していました。
今は 1 回である程度理想のコードが出てくるので、**前みたいに毎日ぐったり疲れ切ることが減りました。**
(個人的にこれが一番うれしかったです！)

## おわりに

意外だったのは、理解の工程を増やしたほうが速くなったこと。

まさに急がば回れでした。

AI に任せる範囲が広がるほど、AI が書いたものを**自分がどれだけ速く理解できるか**が大事になると思ってます。

今は「ここはなぜこうしたの？」と聞かれたときに、コードを調べ直す時間と返信までの時間が短くなりました。

まだ試行錯誤の途中なので、AI で実装は速くなったのにレビューで止まってしまう人がいたら、ぜひやり方を教えてもらえるとうれしいです！
