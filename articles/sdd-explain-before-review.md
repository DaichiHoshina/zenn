仕様駆動開発 (Spec-Driven Development) は、コードより先に仕様を書き、仕様を正として AI に実装させる進め方です。
GitHub の Spec Kit や AWS の Kiro が代表例で、仕様と実装が合っているかを確かめる仕組みも揃ってきました。

自分も Claude Code で仕様駆動開発をしています。
ただ、既存の進め方をそのまま使わず、1 つ工程を足しました。
**AI に説明させて、自分の認識と合っているかを確かめる工程**です。

この記事では、なぜ説明を大事にしているのかと、仕様駆動開発のどこに説明を置いているのかを、1 つの小さな変更を通して紹介します。
例の変更は記事のために用意したサンプルで、設計・実装・説明はどれも Claude Code に実際に出力させたものです。

## なぜ説明を大事にしているか

仕様駆動開発で AI に任せられる範囲は広がりました。
仕様を書けば、設計も実装もテストも AI が進めてくれます。

それでも、レビュワーの前で「なぜこうしたのか」を説明するのは自分です。
仕様と実装が合っていても、自分がその中身を説明できなければ、レビューで答えられません。

仕様と実装の一致は、仕組みで確かめられます。
**実装と自分の理解の一致**は、自分で確かめるしかありません。
説明の工程は、そのためのものです。

## 既存の仕様駆動開発との違い

工程を並べると、違いは最後の行です。

| 工程 | Spec Kit | Kiro | 自分の進め方 |
|---|---|---|---|
| 要件を決める | specify | requirements | PRD、Design Doc |
| 設計する | plan | design | Design Doc、Phase 詳細設計 |
| 作業に分ける | tasks | tasks | 作業計画書 |
| 実装する | implement | タスク実行 | 実装 |
| 仕様との差を確かめる | converge | correctness (プロパティベーステスト) | AI によるレビュー |
| **自分の理解を確かめる** | 一覧に無い | 一覧に無い | **説明** |

Spec Kit と Kiro の列は、2026 年 11 月 1 日時点の各リポジトリの README から取りました。
「一覧に無い」は、README の工程や機能の一覧に、その工程が独立して載っていないことを指します。

## 仕様を 3 段に分けて、説明しやすくする

説明を受けるには、一度に理解する量が少ないほうが楽です。
なので、仕様を 3 段に分け、細かい決定ほど後で決めています。

| 文書 | 決めること | 作るタイミング |
|---|---|---|
| Design Doc | 何を作れば正解か (外から見える動き) | 最初に 1 回 |
| 作業計画書 | どの PR (Phase) で作るか | Design Doc の後 |
| Phase 詳細設計 | どう作るか (関数・SQL・トランザクション) | 各 Phase に着手する直前 |

ここからは、デッドロックを解消する変更を例に、それぞれの文書に何を書き、どこで説明を受けるかを追います。
例の前提は、MySQL (InnoDB)、在庫は商品ごとに 1 行 (`item_id` が一意) です。

## Design Doc: 外から見える動きを、受け入れ条件の表で固定する

例の状況はこうです。
注文の確定処理で、在庫テーブルと注文テーブルを処理ごとに違う順番で更新していて、デッドロックが起きています。

Design Doc では、内部の作りではなく、外から見える動きだけを「〜のとき、〜が〜になる」の形で決めます。

| # | 条件 | 結果 |
|---|---|---|
| 1 | 在庫が足りるとき、保留中の注文を確定する | 在庫が注文の数量だけ減り、注文の状態が確定になる |
| 2 | 在庫が足りないとき | 在庫不足のエラーを返し、在庫も注文も変わらない |
| 3 | 注文が保留中でないとき (確定済み・存在しない) | エラーを返し、在庫も注文も変わらない |
| 4 | 同じ商品の注文を同時に確定するとき | デッドロックが起きず、在庫がマイナスにならない |

(この表は記事のために作った例です)

この表が、後のレビューで「仕様と合っているか」を確かめる基準になります。

## 作業計画書: 1 つの PR を小さくする

作業計画書では、Design Doc を PR 単位の Phase に分けます。
1 つの PR は 1 つの目的に限り、変更の見込みはテストを除いて 400 行まで (設定で変えられる) にしています。
超える PR には、分割しない理由を書かせます。

ここで 1 つ大事な前提があります。
ロックの順番を在庫、注文に揃えても、次のどれかに当たればデッドロックは残ります。

- 注文と在庫を更新する別の処理が、逆の順番のまま
- 呼び出し元が、この処理より前に注文や在庫の行をロックしている
- 1 つのトランザクションで複数の商品の在庫をロックするのに、行の順番 (商品 ID の昇順など) が揃っていない

なので、作業計画書には「在庫と注文を更新するすべての処理を、同じ順番に揃える」ことを Phase の対象として書きます。
この例は、1 つの注文が 1 つの商品だけを持ち、注文を作った後は商品と数量を変更しない、という単純な形にしています。
この記事では、そのうちの 1 つの関数だけを追います。

## Phase 詳細設計と、実装の前の説明

Phase に着手する直前に、実装の方法を決めます。
決めたら、実装に入る前に、設計を AI に説明させます。

聞くのは、どの層にどの責務を置くか、なぜその設計か、採用しなかった案、処理の順番の 4 つです。
依頼はこうしました。

```text
これから実装する変更の、実装前の設計の説明をしてください。
変更: 注文の確定処理で、在庫テーブルと注文テーブルを処理ごとに異なる順番で更新していて、デッドロックが起きている。
更新の順番を在庫、注文の順に統一し、在庫の行は SELECT ... FOR UPDATE で先に取得する。Go のリポジトリ層の関数 1 つに閉じる。
説明は、どの層にどの責務を置くか、なぜその設計か、採用しなかった案、処理の順番、の 4 点で。
```

実際に返ってきた説明から抜粋します (公開しているプラグインの `/sdd:explain` は、実装前の説明に作業計画書が必要なので、この説明はいつもの環境の Claude Code に上の依頼をして出力したものです)。

> **責務の置き場所**
> - トランザクションの開始と終了は、呼び出し元 (サービス層) が持ちます。
> - 在庫の行のロック、在庫の更新、注文の更新の順番は、リポジトリ層の関数 1 つに閉じ込めます。
>
> **採用しなかった案**
> - リトライでデッドロックを回避する案: 原因が残るので、再実行が増えるだけです。
> - 分離レベルを上げる案: 影響範囲が広く、1 関数の修正では済みません。

ここで、自分が考えていた設計と 1 つずつ比べます。

採用しなかった案の書き方は、少し強すぎます。
リトライは、デッドロックで中断された処理を回復する手段として有効です。
この例では、ロックの順番の統一を主な対策にし、リトライは中断されたときの補助として扱います。説明の言い過ぎに気づけるのも、自分の認識と並べて読むからです。

## 実装と、見つかったずれ

最初の実装は、関数の中で `db.BeginTx` を呼び、自分でトランザクションを始めていました。
実装の前の説明と並べると、ずれています。

| | 言っていること |
|---|---|
| 実装の前の説明 | トランザクションの開始と終了は、呼び出し元が持つ |
| 最初の実装 | 関数の中で `db.BeginTx` を呼び、自分でトランザクションを始めている |

どちらが正しいかは、この時点では決まりません。
呼び出し元がすでにトランザクションを持っているなら、関数の中で `db.BeginTx` を呼んでも、そのトランザクションには加わらず、別のトランザクションになってしまいます。

この例では、呼び出し元がトランザクションを持つ設計に合わせて、`*sql.Tx` を受け取る形に修正しました。
あわせて、商品と数量は引数で受け取らず注文の行から読み、受け入れ条件の 3 (保留中でない注文) を満たすように、更新した行数も確かめるようにしています。

:::details 修正後のコード (Go)
```go
package order

import (
	"context"
	"database/sql"
)

// Confirm は保留中の注文を確定する。トランザクションは呼び出し元が開始と終了を受け持つ。
// 在庫、注文の順に行をロックしてから更新する。呼び出し元はこの関数より前に注文や在庫の行をロックしない前提。
func Confirm(ctx context.Context, tx *sql.Tx, orderID int64) error {
	var itemID int64
	var qty int
	if err := tx.QueryRowContext(ctx,
		"SELECT item_id, quantity FROM orders WHERE id = ? AND status = 'pending'", orderID,
	).Scan(&itemID, &qty); err != nil {
		if err == sql.ErrNoRows {
			return ErrNotConfirmable
		}
		return err
	}
	if qty <= 0 {
		return ErrInvalidQty
	}

	var stock int
	if err := tx.QueryRowContext(ctx,
		"SELECT quantity FROM inventories WHERE item_id = ? FOR UPDATE", itemID,
	).Scan(&stock); err != nil {
		return err
	}
	if stock < qty {
		return ErrOutOfStock
	}
	if _, err := tx.ExecContext(ctx,
		"UPDATE inventories SET quantity = quantity - ? WHERE item_id = ?", qty, itemID,
	); err != nil {
		return err
	}

	res, err := tx.ExecContext(ctx,
		"UPDATE orders SET status = 'confirmed' WHERE id = ? AND status = 'pending'", orderID,
	)
	if err != nil {
		return err
	}
	n, err := res.RowsAffected()
	if err != nil {
		return err
	}
	if n != 1 {
		return ErrNotConfirmable
	}
	return nil
}
```

呼び出し元は、トランザクションの開始・rollback・commit を受け持ちます。

```go
package order

import (
	"context"
	"database/sql"
)

// ConfirmOrder はトランザクションを開始して注文を確定する。
// Confirm がエラーを返したら rollback し、在庫の減算も取り消す。
func ConfirmOrder(ctx context.Context, db *sql.DB, orderID int64) error {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer tx.Rollback()

	if err := Confirm(ctx, tx, orderID); err != nil {
		return err
	}
	return tx.Commit()
}
```

`ErrOutOfStock` などのエラーは、同じパッケージの別ファイルで定義しています。
:::

実装したら、観点ごとに別のサブエージェント (Claude Code の中で並列に動く別の AI) にレビューさせます。
観点は、Design Doc と作業計画書との比較、チームの過去のレビュー指摘の傾向、リポジトリ独自の規約、言語の開発指針の 4 つです。
仕様と実装が合っているかは、ここで確かめます。

## 実装の後の説明

PR を draft で作ったら、今度はコードを説明させます。
依頼は `/sdd:explain` の 1 行だけです。
引数を付けなければ、作業中の差分が対象になります。

ここからは、公開しているプラグインの `/sdd:explain` を、この例のリポジトリで実際に実行した出力です。
説明は「一言でいうと」「どう動くか」「変更前との違い」「影響範囲と注意点」などの順に返ってきます。
その中に、こんな注意点がありました。

> `Confirm` の doc comment には「呼び出し元はこの関数より前に注文や在庫の行をロックしない」とあります。別の処理が注文を先にロックして在庫を後に取ると、ロック順が逆になって deadlock の恐れがあります。この点は呼び出し元の約束に頼っており、code では防げていません。

最後には、理解を確認する問いが付きます。

> **確認したい点**
> 1. 同じ注文が同時に 2 回確定されたとき、在庫が 1 回分しか減らないのは、どの手順のどの条件のおかげですか
> 2. `Confirm` が失敗したとき、手順 6 で減らした在庫が元に戻るのはなぜですか
> 3. 変更前の `Confirm` では起きえた、在庫に関する問題は何ですか

答えは折りたたまれているので、先に自分で答えてから開きます。

2 つ目は、受け入れ条件の 3 と直接つながっています。
「エラーを返すから在庫は変わらない」と答えたなら、在庫が戻るのは呼び出し元の `ConfirmOrder` が rollback するからだ、という前提を自分が持てていなかったことになります。
レビューで「エラーのとき在庫は戻る？」と聞かれたら、答えられなかった箇所です。

## 認識と合わないとき

大事なのは、AI の説明が正しいかどうかより、**自分の認識と合っているか**です。
合わなかったときは、AI が間違えていることもあれば、自分の理解が間違えていることもあります。
どちらにしても、ずれた箇所はレビューで聞かれやすい箇所なので、コードを読み直すか AI に聞き返して、ずれが無くなってから draft を解除し、レビューを依頼します。

ずれが無いからといって、正しいとは限りません。AI と自分が同じ誤解をしていれば、ずれは見えないからです。
なので、ずれはあくまで入口にして、最後はコード・受け入れ条件・テストで確かめます。

説明が分からなければ、読み手を変えてもう一度説明させます。
入力履歴から、実際に打った言葉です。

```text
DB初心者向けに上記を説明
中学生向けで
ジョインしたてエンジニア向け
```

## 説明の工程を足してみて

レビューで初めて見つかる問題と、レビューの往復は減りました。
ただ、PR を小さくしたことや AI のレビューも同時に始めたので、説明の工程だけの効果は分かりません。
件数を集計したわけでもない、自分の体感です。

それでも、仕様駆動開発で AI に任せる範囲が広がるほど、自分が説明できることの価値は上がっていくと思っています。

## 自分が使っている道具

この進め方のコマンドは、sdd というプラグインにまとめて公開しています。
Design Doc は `/sdd:design`、作業計画書は `/sdd:plan`、説明は `/sdd:explain`、レビューは `/sdd:review` です。

https://github.com/DaichiHoshina/daidai

```text
/plugin marketplace add DaichiHoshina/daidai
/plugin install sdd@daidai
```

入れたら、導入先のリポジトリで `/sdd:init` を実行し、差分がある状態で `/sdd:explain` と打てば、実装の後の説明を試せます。
