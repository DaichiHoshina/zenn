AI に実装を任せるようになってから、自分のコードの理解をどう保っているかの棚卸しです。

きっかけは、レビューで「ここはなぜこうしたの？」と聞かれて、自分の PR なのに即答できなかったことでした。
巨大なモノリスの現場で、実装は速くなったのに開発全体はかえって遅くなり、体調まで崩しました。

## 原則: レビュー依頼のときに、自分の言葉で説明できること

- ゴールは速く書くことではなく、**レビュワーの前で中身を説明できる状態**にすること
- 書く作業も PR を作る作業も AI に任せていい。説明するのは自分
- 説明できない箇所が 1 つでもあれば、レビューはまだ依頼しない

## 仕様: 細かい決定ほど後で決める

最初に細部まで決めると、前の PR の実装で前提が変わって作り直しになります。
なので、文書を 3 段に分けています。

| 文書 | 決めること | 作るタイミング |
|---|---|---|
| Design Doc | 何を作れば正解か (外から見える動き) | 最初に 1 回 |
| 作業計画書 | どの PR (Phase) で作るか | Design Doc の後 |
| Phase 詳細設計 | どう作るか (メソッド・SQL・トランザクション) | 各 Phase の着手直前 |

- 外から見える動きは「〜のとき、〜が〜になる」の受け入れ条件の表で固定する。仕様の抜けに、実装やレビューで初めて気づくのを防ぐため
- 1 Phase = 1 PR で、変更はテストを除いて 400 行まで。スクリプトで検査している
- 既存の処理を置き換えるときは、切り替えの PR と、古い処理を消す PR を最初から分けておく。不具合が見つかっても、切り替えだけを戻せる

## 理解: 実装の前と後で、AI に説明させる

一番効果があると感じているのがここです。

- 実装前は設計を説明させる: どの層にどの責務を置くか、なぜその設計か、処理がどの順で進むか
- 実装後はコードを説明させる: どの関数が何を受け取り何を返すか、テストが何を保証するか
- 説明の終わりに、理解を確認する問いを 1〜5 個返させる。答えは折りたたんであるので、先に自分で考えてから開く
- 答えられなかった問いが、自分の理解の足りないところ

一度で分からなければ、読み手を変えて説明し直させます。
実際にチャットで打っているのはこんな言葉です (入力履歴から。コマンド名だけ、後で紹介するプラグインの形に揃えています)。

```text
/sdd:explain DB初心者向けに上記を説明
/sdd:explain 中学生向けで
/sdd:explain ジョインしたてエンジニア向け
/sdd:explain 指摘について説明して
```

## レビュー: 人に見せる前に、観点ごとに AI に見せる

- 観点ごとに別のサブエージェント (Claude Code の中で並列に動く別の AI) を起動して、差分をレビューさせる
- 観点は 4 つ: 設計書との比較 / チームの過去のレビュー指摘の傾向 / リポジトリ独自の規約 / 言語の開発指針
- 指摘は Critical と Warning に分け、どちらも 0 件になってから PR を作る
- 規約や命名の指摘は、ここでほぼ片づく。人のレビューの往復が減る

```text
/sdd:review 最後に全体みてほしい
/sdd:review 再度必要なルールを読み込んでレビュー
```

## PR: draft で作って、説明と自分の認識を突き合わせる

- PR はまず draft で作る
- draft の差分を AI に説明させ、自分の認識と一致したら draft を解除してレビューを依頼する
- ずれていたら、そこが説明できない箇所。依頼の前に修正する

## 使っている道具

ここまでのコマンドは、sdd というプラグインにまとめて公開しています。

https://github.com/DaichiHoshina/daidai

```text
/plugin marketplace add DaichiHoshina/daidai
/plugin install sdd@daidai
```

入れたら、導入先のリポジトリで `/sdd:init` を実行します。
言語は問いません (同梱の開発指針は Go と TypeScript)。

:::details コマンドの一覧
| コマンド | やること |
|---|---|
| `/sdd:init` | 設定ファイルと成果物の置き場所を作る |
| `/sdd:prd` | 対話で要件を集めて PRD (何のために何を作るかの文書) を作る |
| `/sdd:design` | 受け入れ条件の表で振る舞いを固定した Design Doc を作る |
| `/sdd:plan` | Design Doc を 1 Phase = 1 PR の作業計画書に分ける |
| `/sdd:phase-design` | Phase 1 つの実装方法を、既存コードを調べてから決める |
| `/sdd:explain` | 実装前は設計を、実装後は差分のコードを説明する |
| `/sdd:implement` | Phase を 1 つ実装し、完了条件をコマンドで確認する |
| `/sdd:review` | 差分を観点ごとに並列でレビューする |
| `/sdd:status` | Phase の進み具合と、この後に実行するコマンドを表示する |
:::

## 変わったこと

- レビューで初めて見つかる問題と、レビューコメントの数が減った。返信や修正の時間も短くなった
- 実装を何回も出力し直すことが減り、毎日ぐったり疲れ切ることが減った。個人的にはこれが一番うれしい
- 「ここはなぜこうしたの？」と聞かれたときに、コードを調べ直す時間と返信までの時間が短くなった

工程は増えたのに、全体は速くなりました。
どれも数字では測っていない、自分の体感です。

AI に任せる範囲が広がるほど、AI が書いたものを自分がどれだけ速く理解できるかが大事になる気がしています。

やり方はまたすぐ変わると思います。
同じように悩んでいる人のやり方も、ぜひ教えてください！
