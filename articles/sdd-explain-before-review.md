AI に実装を任せると、コードは速くできます。
ただ、自分がそのコードを説明できるかは別の話です。

この記事では、Claude Code に書かせた変更を、レビューを依頼する前に Claude Code 自身に説明させ、自分の認識と突き合わせる進め方を、1 つの小さな変更で最初から最後まで追います。
読み終えたら、使っている AI が何であっても、同じ確認を自分の作業に組み込めるはずです。

## 題材: デッドロックを解消する 1 つの関数

注文の確定処理で、在庫テーブルと注文テーブルを処理ごとに違う順番で更新していて、デッドロックが起きていたとします。
直し方は、更新の順番を在庫、注文の順に統一し、在庫の行を `SELECT ... FOR UPDATE` で先にロックすることです。

この変更を、実装の前に 1 回、実装の後に 1 回、AI に説明させます。

## 実装の前: 設計を説明させる

実装の前に聞くのは、どの層にどの責務を置くか、なぜその設計か、採用しなかった案、処理の順番の 4 つです。
実際に返ってきた説明から抜粋します。

> **責務の置き場所**
> - トランザクションの開始と終了は、呼び出し元 (サービス層) が持ちます。
> - 在庫の行のロック、在庫の更新、注文の更新の順番は、リポジトリ層の関数 1 つに閉じ込めます。
>
> **採用しなかった案**
> - リトライでデッドロックを回避する案: 原因が残るので、再実行が増えるだけです。
> - 分離レベルを上げる案: 影響範囲が広く、1 関数の修正では済みません。
> - サービス層でロック順を管理する案: 層をまたぐと責務が散らばるため、今回は見送りました。

ここで、自分の考えていた設計と 1 つずつ比べます。
採用しなかった案の中に自分が検討していなかった案があれば、そこで初めて気づけます。

## 実装の後: コードを説明させる

実装はこうなりました。

:::details 変更したコード (Go)
```go
package order

import (
	"context"
	"database/sql"
)

// Confirm は注文を確定する。在庫、注文の順に行をロックしてから更新する。
func Confirm(ctx context.Context, db *sql.DB, orderID, itemID int64, qty int) error {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer tx.Rollback()

	var stock int
	if err := tx.QueryRowContext(ctx,
		"SELECT quantity FROM inventories WHERE item_id = ? FOR UPDATE", itemID,
	).Scan(&stock); err != nil {
		return err
	}
	if stock < qty {
		return ErrOutOfStock
	}
	if _, err := tx.ExecContext(ctx,
		"UPDATE inventories SET quantity = quantity - ? WHERE item_id = ?", qty, itemID,
	); err != nil {
		return err
	}
	if _, err := tx.ExecContext(ctx,
		"UPDATE orders SET status = 'confirmed' WHERE id = ?", orderID,
	); err != nil {
		return err
	}
	return tx.Commit()
}
```
:::

実装の後に聞くのは、どの関数が何を受け取り何を返すか、なぜこの順番か、テストで何を確かめるか、です。
最後に、理解を確認する問いを付けてもらいます。

> **理解を確認する問い**
> 1. 2 つの処理がデッドロックになる、行のロックの取り合いを説明してください。
> 2. 在庫を読む SELECT に `FOR UPDATE` が必要な理由は何ですか。
> 3. 注文の更新で失敗したとき、在庫の減算はどうなりますか。

答えは折りたたんでもらい、先に自分で答えてから開きます。
3 つ目に「在庫は減ったまま」と答えたなら、`defer tx.Rollback()` がトランザクションごと取り消すことを分かっていなかった、ということです。

説明には「`ErrOutOfStock` の定義はこのファイルに無く、未確認です」のように、AI が確かめていない点も含まれていました。
そこは自分でファイルを開いて確かめます。

## ずれた箇所: トランザクションは誰が始めるのか

2 つの説明を並べると、ずれが 1 つ見つかります。

| | 言っていること |
|---|---|
| 実装の前の説明 | トランザクションの開始と終了は、呼び出し元が持つ |
| 実装したコード | `Confirm` の中で `db.BeginTx` を呼び、自分でトランザクションを始めている |

どちらが正しいかは、この時点では決まりません。
呼び出し元がすでにトランザクションを持っているなら、コードのほうを修正する必要があります。
`Confirm` だけで完結させる方針なら、設計の説明のほうが自分の意図とずれています。

大事なのは、AI の説明が正しいかどうかより、**自分の認識と合っているか**です。
合わなかったときは、AI が間違えていることもあれば、自分の理解が間違えていることもあります。
どちらにしても、ずれた箇所はレビューで聞かれる箇所なので、コードを読み直すか AI に聞き返して、ずれが無くなってからレビューを依頼します。

## 一度で分からないとき

説明が分からなければ、読み手を変えてもう一度説明させます。
自分の入力履歴から、実際に打った言葉です。

```text
DB初心者向けに上記を説明
中学生向けで
ジョインしたてエンジニア向け
指摘について説明して
```

分からないまま次に進まないことだけを決めています。

## この確認を、作業の流れのどこに置くか

自分は、1 つの PR を次の順に進めています。

1. 実装の方法を決め、実装の前の説明を受ける
2. 実装する
3. 観点ごとに AI にレビューさせ、指摘が無くなるまで修正する
4. PR を draft で作り、実装の後の説明を受ける
5. 説明と自分の認識が合ったら、draft を解除してレビューを依頼する

説明を受けるには、差分が小さいほうが楽です。
なので、1 つの PR は 1 つの目的に限り、変更の見込みが大きいときは計画の段階で分けています。

レビューで初めて見つかる問題と、レビューの往復は減りました。
ただ、PR を小さくしたことや AI のレビューも同時に始めたので、説明の工程だけの効果は分かりません。
件数を集計したわけでもない、自分の体感です。

## 自分が使っている道具

この流れのコマンドは、sdd というプラグインにまとめて公開しています。
説明は `/sdd:explain`、観点ごとのレビューは `/sdd:review` です。

https://github.com/DaichiHoshina/daidai

```text
/plugin marketplace add DaichiHoshina/daidai
/plugin install sdd@daidai
```

この記事の説明の例は、プラグインではなく、自分のいつもの環境の Claude Code に同じ内容を頼んで出力したものです。
説明させて突き合わせるだけなら、プラグインが無くても、どの AI でもできます。
