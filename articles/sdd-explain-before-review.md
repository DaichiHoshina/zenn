## 即答できなかった日

> 「ここはなぜこうしたの？」

レビューでこう聞かれて、答えられませんでした。
自分の PR です。

コードを書いたのは Claude Code で、自分の理解は浅いままでした。
なぜその形なのかを、自分の言葉で説明できませんでした。

一度ではなく、何度も同じことが起きました。

## 速くなったのに、遅くなった

現場は巨大なモノリスのプロジェクトです。

AI のおかげで、実装そのものは速くなりました。
ただ、レビューで聞かれては調べ直し、指摘を受けては実装を出し直す。
その往復が増えて、開発全体はかえって遅くなり、品質も上がりませんでした。

何回も実装を出力し直す毎日で、ぐったり疲れ切って、体調まで崩しました。

さすがにまずい、と。

振り返ると、問題は実装の速さではありませんでした。
**自分が理解しないまま、次の工程へ進んでしまうこと**でした。

## 理解する工程を、先に入れた

そこで、レビューを依頼する前に、AI にコードを説明させる工程を入れました。
ゴールは、レビュワーの前で中身を自分の言葉で説明できる状態です。
書く作業も PR を作る作業も AI に任せて構いません。
説明するのは自分です。

説明させるのは、実装の前と後の 2 回です。

| タイミング | 説明させること |
|---|---|
| 実装の前 | どの層にどの責務を置くか、なぜその設計か、処理がどの順で進むか |
| 実装の後 | どの関数が何を受け取り何を返すか、テストが何を保証するか |

説明の終わりには、理解を確認する問いが 1〜5 個返ってきます。
答えは折りたたんであるので、先に自分で考えてから開きます。
答えられなかった問いが、自分の理解の足りないところです。

ただ、説明も確認の問いも同じ AI が作るので、説明そのものが間違っていれば、一緒に間違えて納得してしまいます。

一度で分からなければ、読み手を変えて説明し直させます。
入力履歴から、実際に打った言葉を抜き出しました (コマンド名は後で紹介するプラグインの形に揃えています)。

```text
/sdd:explain DB初心者向けに上記を説明
/sdd:explain 中学生向けで
/sdd:explain ジョインしたてエンジニア向け
/sdd:explain 指摘について説明して
```

1 つの Phase は、実装、AI によるレビュー、draft の PR の作成、説明と自分の認識の突き合わせ、の順に進めます。
認識が一致したら draft を解除して、レビューを依頼します。

## 説明を受けやすくするために、PR を小さくした

説明を受けても、差分が大きいと理解が追いつきません。
なので、仕様の段階から PR を小さく分けるようにしました。

- 仕様は PR 単位の Phase に分け、1 Phase = 1 PR にする。作業計画書の段階で、各 PR の変更の見込みをテストを除いて 400 行まで (設定で変えられる) にし、超える PR には分割しない理由を書かせる。これはスクリプトで検査している
- 外から見える動きは、実装の前に「〜のとき、〜が〜になる」の受け入れ条件の表で固定する
- 実装方法 (メソッド・SQL・トランザクション) は、その Phase に着手する直前に、既存コードを調べてから決める。前の Phase の実装で前提が変わっても、細かい実装方法を先に決めすぎていない分、設計のやり直しを小さく抑えられる
- 既存の処理を置き換えるときは、切り替えの PR と、古い処理を消す PR を最初から分けておく

## 人に見せる前に、AI に見せた

規約や命名の指摘でレビューが往復するのも、減らしたかったことです。
レビューを依頼する前に、観点ごとに別のサブエージェント (Claude Code の中で並列に動く別の AI) に差分を見せています。

| 観点 | 確認すること |
|---|---|
| 設計書との比較 | 作業計画書の範囲と受け入れ条件に沿っているか |
| 過去の指摘 | チームの過去のレビュー指摘の傾向と比べる |
| リポジトリの規約 | リポジトリ独自の規約に沿っているか |
| 言語の指針 | 使っている言語の開発指針に沿っているか |

指摘は Critical と Warning に分け、どちらも 0 件になってから PR を作ります。

## それから

工程は増えました。
それでも、全体は速くなりました。

レビューで初めて見つかる問題と、レビューコメントの数が減り、返信や修正の時間も短くなりました。
実装を何回も出し直すことが減り、毎日ぐったり疲れ切ることも減りました。
個人的には、これが一番うれしかったことです。
どれも件数を集計したわけではない、自分の体感です。
PR を小さくしたことや AI のレビューも同時に始めたので、説明の工程だけの効果は分かりません。

今は「ここはなぜこうしたの？」と聞かれたときに、コードを調べ直す時間と返信までの時間が短くなりました。

## 同じ流れを試すなら

ここまでのコマンドは、sdd というプラグインにまとめて、自作のプラグインの配布元 daidai で公開しています。

https://github.com/DaichiHoshina/daidai

```text
/plugin marketplace add DaichiHoshina/daidai
/plugin install sdd@daidai
```

入れたら、導入先のリポジトリで `/sdd:init` を実行します。
言語は問いません (同梱の開発指針は Go と TypeScript)。

:::details コマンドの一覧
| コマンド | やること |
|---|---|
| `/sdd:init` | 設定ファイルと成果物の置き場所を作る |
| `/sdd:prd` | 対話で要件を集めて PRD (何のために何を作るかの文書) を作る |
| `/sdd:design` | 受け入れ条件の表で振る舞いを固定した Design Doc を作る |
| `/sdd:plan` | Design Doc を 1 Phase = 1 PR の作業計画書に分ける |
| `/sdd:phase-design` | Phase 1 つの実装方法を、既存コードを調べてから決める |
| `/sdd:explain` | 実装前は設計を、実装後は差分のコードを説明する |
| `/sdd:implement` | Phase を 1 つ実装し、完了条件をコマンドで確認する |
| `/sdd:review` | 差分を観点ごとに並列でレビューする |
| `/sdd:status` | Phase の進み具合と、この後に実行するコマンドを表示する |
:::

AI に任せる範囲が広がるほど、AI が書いたものを自分がどれだけ速く理解できるかが、開発の速さを決めるようになると思っています。
