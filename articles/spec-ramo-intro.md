## AI が書いた PR を、自分で説明できますか

Claude Code で実装を任せるようになってから、実装そのものにかかる時間はかなり短くなりました。一方で、レビューや手戻りまで含めた開発全体は、かえって遅くなっていました。

きっかけは、巨大なモノリスのプロジェクトでした。普通に AI に実装を任せたところ、開発にもレビューにもかなり時間がかかり、品質も低いままでした。AI が生成したコードを自分で把握しきれず、毎日頭が疲れて、体調まで悪くなっていました。

チームの開発で目立った困りごとは、次の 4 つです。

| 困りごと | 何が起きていたか |
|---|---|
| PR の大きさ | 1 本の PR を読むのに時間がかかり、PR のリードタイムが延びる |
| 仕様の判断 | 仕様で決めていなかった点に、実装やレビューの段階で気づく |
| AI コードの理解 | 実装者より先に、レビュワーが問題に気づく |
| レビューの負担 | 差分だけでは仕様を読み取れず、PR の内容の理解に時間がかかる |

特につらかったのは、表の 3 つ目の「AI コードの理解」です。自分の PR なのに、レビューで「ここはなぜこうしたの？」と聞かれて即答できない。速く作れるようになった分、「自分が理解しないまま進んでしまう」ことがボトルネックになっていました。

そこで、チーム向けに組み立てた spec 駆動開発の手順を Claude Code のプラグインにまとめました。それが Spec Ramo (スペックラモ) です。

## Spec Ramo とは

仕様を PR 単位の Phase に分け、実装者が理解してから Phase を 1 つずつ進める、spec 駆動開発の Claude Code プラグインです。

名前は spec (仕様) + ramo (スペイン語・イタリア語で「枝」) から来ています。1 つの仕様から、Phase ごとの PR へ枝分かれしていくイメージです。

先ほどの 4 つの困りごとに、1 つずつ対応しています。

| 困りごと | Spec Ramo での対応 |
|---|---|
| PR の大きさ | 1 Phase = 1 PR にし、目的を 1 つだけにする。変更の上限 400 行 (テスト除く) を script で検査する。チームでは目安を 200 行にしている |
| 仕様の判断 | 実装の前に Design Doc で、見える動きを受け入れ条件の表に固定する |
| AI コードの理解 | 実装の前後に `/specramo:explain` で説明を読み、自分の言葉で説明できてから進む |
| レビューの負担 | 規約や命名の指摘は、レビュー依頼の前に AI レビューで 0 件にする |

## 一般的な spec 駆動開発との違い

spec 駆動開発は、コードより先に仕様を書き、仕様を正として実装する手法です。代表例は GitHub の Spec Kit と AWS の Kiro です。工程を並べると次のように対応します。

| 工程 | Spec Kit | Kiro | Spec Ramo |
|---|---|---|---|
| 要件を決める | specify | requirements | `/specramo:prd`・`/specramo:design` |
| 設計する | plan | design | `/specramo:design`・`/specramo:phase-design` |
| 作業に分ける | tasks | tasks | `/specramo:plan` |
| 実装する | implement | タスク実行 | `/specramo:implement` |
| 差を確かめる | converge | なし | `/specramo:review` |
| 理解を確かめる | なし | なし | `/specramo:explain` |

違いは一番下の行です。仕様と実装の一致を確かめる仕組みは既存の手法にもあります。Spec Ramo は、それに加えて実装者の理解を確かめる工程を設けました。

## 使い方: PRD から PR まで

コマンドは次の順に使います。

| 順 | コマンド | すること |
|---|---|---|
| 1 | `/specramo:init` | 設定ファイルと成果物の置き場所を作る |
| 2 | `/specramo:prd` | 対話で要件を集めて PRD を作る |
| 3 | `/specramo:design` | 受け入れ条件の表で振る舞いを固定した Design Doc を作る |
| 4 | `/specramo:plan` | Design Doc を 1 Phase = 1 PR の作業計画書に分ける |
| 5 | `/specramo:phase-design` | Phase 1 つの実装方法を、既存コードを調べてから決める |
| 6 | `/specramo:explain` | 実装前に Phase の設計を説明する |
| 7 | `/specramo:implement` | Phase を 1 つ実装し、完了条件をコマンドで確かめる |
| 8 | `/specramo:review` | 差分を 4 観点で並列にレビューする |
| 9 | `/specramo:explain` | 実装後に差分のコードを説明する |
| - | `/specramo:status` | Phase の進み具合と、この後に実行するコマンドを表示する |

1〜4 は最初に 1 回だけ、5〜9 は Phase ごとに繰り返します。

**PR は自分で作ります。** Spec Ramo は PR を作りません。9 の説明を読んで「自分の言葉で説明できる」と思えたら、自分の手で PR を作り、レビューを依頼してから次の Phase に進みます。次の Phase に進むかどうかも、実装者の判断です。この一手を人間の担当にしたのが一番のこだわりです。

## こだわったところ

### 1. 決めることの細かさで文書を分ける

文書は 3 種類あり、細かい決定ほど後で、着手の直前に決めます。

| 文書 | 決めること | 記載する決定 | 作る時点 |
|---|---|---|---|
| Design Doc | 何を作れば正解か | 見える動きが変わる決定 | 最初に 1 回 |
| 作業計画書 | どの Phase で作るか | 作り方だけが変わる決定 | Design Doc の後 |
| Phase 詳細設計 | どう作るか | メソッド・SQL・トランザクション | 各 Phase の着手直前 |

分けておくと、読む範囲が狭くなり、着手する Phase の実装方法だけを読めば済みます。実装方法は既存コードを調べてから決めるので、手戻りも減ります。

作業計画書には、マージしても本番が壊れない順に Phase を並べます。Phase 詳細設計は、トランザクションの範囲や排他制御のように未決の判断がある Phase だけで作り、既存コードと同じ書き方で済む Phase では省きます。

### 2. 文章で頼まず、script で確かめる

AI に「〜を確認してください」と書いても、確認されないことがあります。そこで、守ってほしいことはなるべく検査 script にしました。AI が文書を作った後に検査を実行し、FAIL が 0 件になるまで AI が文書を書き換えます。人が読むのはその後の文書です。

| 検査 | 対象 | 主な判定 |
|---|---|---|
| `dd-gate` | Design Doc | 未確定の項目が無い / 既存の制約 (一意・外部キーなど) を緩めるなら、引き継ぐ仕組みとそのコードの位置を記載した |
| `spec-gate` | 作業計画書 | 各 PR に想定行数がある / 400 行を超える PR に分割しない理由がある / メソッド名や SQL を記載していない |
| `phase-gate` | Phase 詳細設計 | 意味が変わる table を読む既存の query を全件洗い出した |

例として `phase-gate` を取り上げます。論理削除 (`deleted_at`) を追加すると、その table を読む既存の query すべてに条件の追加が必要で、1 件でも見落とすと、管理画面などで消したはずのデータが表示されてしまいます。そこで、Phase 詳細設計に「table を読む query は合計 n 件」と記載させ、script が数えた件数と一致しなければ FAIL にしています。

```text
FAIL  table-readers  「table を読む query」の節が無い (scripts/table-readers.sh の出力を貼る)
```

「調べました」という文章ではなく、件数の一致で調べたことを確かめる、という考え方です。

### 3. 説明は「時点」で分ける

`/specramo:explain` は、同じコマンドでも実装前と実装後で説明する中身が変わります。

- 実装前: どの層にどの責務を置くか、なぜその設計にしたか、処理がどの順序で進むか。コードの逐行説明はしない
- 実装後: どの関数が何を受け取り何を返すか、テストが何を保証するか

説明の末尾では、理解を確かめる質問を 1 つ返します。説明と自分の理解が一致するまで、AI との対話を繰り返します。

レビューで未解決の指摘がある箇所は、「正しい前提」として説明しないようにしています。失敗すると分かっている SQL を「これで完了します」と説明されると、理解したつもりで間違った PR を作ってしまうからです。

### 4. レビューは観点ごとに別の AI で

`/specramo:review` は、観点ごとに別のエージェントを並列に起動します。

| エージェント | 確認すること |
|---|---|
| 設計書との比較 | 差分が作業計画書の範囲と受け入れ条件に沿っているか。対象外のファイルを変更していないか |
| 過去の指摘 | チームの過去のレビュー指摘の傾向と比べる |
| repo の規約 | repo 独自の規約に沿っているか (規約があるときだけ) |
| 言語の指針 | 使っている言語の開発指針に沿っているか |

指摘は 1 つの一覧にまとめ、Critical と Warning が 0 件になってから PR を作ります。汎用のレビューでは拾えないチーム固有の指摘も、人のレビューの前に見つけられます。

## 使いどころと使わないところ

言語やアーキテクチャは問わず、Web API / CLI / ライブラリ / バッチ / フロントエンドのどれでも使えます。言語別の指針は、今のところ Go と TypeScript の 2 つを同梱しています。

全工程を使うのは、ある程度大きな変更だけです。

| 変更の規模 | 進め方 |
|---|---|
| 数行の修正 | Spec Ramo を使わず、そのまま実装する |
| 単一サービス内の機能追加 | `/specramo:prd` で要件を 1 枚にまとめるだけにする |
| 複数サービスにまたがる変更、API・DB・画面が変わる変更 | 全工程を使う |
| 破壊的変更・データ移行 | 行数が小さくても全工程を使う |

## 導入

Claude Code の session で次の 2 つを実行します。

```text
/plugin marketplace add DaichiHoshina/spec-ramo
/plugin install specramo@specramo
```

インストールしたら、導入先の repo で `/specramo:init` を実行します。

## 使ってみてどうだったか

モノリスのプロジェクトで、spec 駆動の進め方に「自分で理解する工程」を加えて開発しました。変化は 3 つです。

- 品質が上がった。実装者が理解してから PR を作るので、レビューで初めて見つかる問題が減った
- 結果として、開発全体が速くなった。1 工程は増えたものの、レビューの往復と手戻りが減った分のほうが大きかった
- 頭の負担が減った。1 回に考える範囲が 1 Phase だけになり、以前のように毎日疲れ切ることがなくなった

意外だったのは、理解の工程を増やしたほうが速くなったことです。急がば回れでした。

## まとめ

- AI で速く作れるようになった分、ボトルネックは「自分が理解しているか」に移った
- Spec Ramo は、仕様を 1 Phase = 1 PR に分け、説明と質問で理解を確かめてから進める
- Spec Kit や Kiro との違いは、実装者の理解を確かめる工程がある点
- 守ってほしいことは文章でなく script で検査する

AI に任せる範囲が広がるほど、「自分で説明できる PR」を作り続ける仕組みが必要になると考えています。ぜひ試してみてください。
