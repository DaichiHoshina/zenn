## AI が書いた PR を、自分で説明できますか

> 「ここはなぜこうしたの？」

レビューでこう聞かれて、**自分の PR なのに即答できなかった**ことがあります。

コードを書いたのは AI。
実は、自分の理解は浅いままでした。
毎回コードを読んで確認してから、返信するような状態・・・。

舞台は巨大なモノリスのプロジェクトです。
実装は AI でめちゃくちゃ速くなったのに、レビューや手戻りまで含めると、開発はかえって遅くなってました。

品質も低いまま。
毎日頭がぐったり疲れて、体調まで悪くなってました。

これはさすがにまずい、と。

そこで、チーム向けに組み立てた spec 駆動開発の手順を、Claude Code のプラグインにまとめました。
それが Spec Ramo (スペックラモ) です！

## Spec Ramo とは

:::message
仕様を PR 単位の Phase に分けて、実装者が理解してから Phase を 1 つずつ進める、spec 駆動開発の Claude Code プラグインです。
:::

名前は「スペック」と「クラモ」(サンスクリット語で「順序・段階」) を重ねた造語です。

チームで困っていたことと、その対応はこうです。

| 困りごと | Spec Ramo での対応 |
|---|---|
| PR が大きく、読むのに時間がかかる | 1 Phase = 1 PR にし、変更の上限 400 行 (テスト除く) をスクリプトで検査する。チームでは目安を 200 行にしている |
| 仕様で決めていなかった点に、実装やレビューで気づく | 実装の前に Design Doc で、見える動きを受け入れ条件の表に固定する |
| 実装者より先に、レビュワーが問題に気づく | 実装の前後に `/specramo:explain` で説明を読み、自分の言葉で説明できてから進む |
| 差分だけでは仕様を読み取れず、レビューが重い | 規約や命名の指摘は、レビュー依頼の前に AI レビューで 0 件にする |

特につらかったのは 3 行目、冒頭の場面です。

## 一般的な spec 駆動開発との違い

spec 駆動開発は、コードより先に仕様を書く手法です。
代表例は GitHub の Spec Kit と AWS の Kiro ですね。

| 工程 | Spec Kit | Kiro | Spec Ramo |
|---|---|---|---|
| 要件を決める | specify | requirements | `/specramo:prd`・`/specramo:design` |
| 設計する | plan | design | `/specramo:design`・`/specramo:phase-design` |
| 作業に分ける | tasks | tasks | `/specramo:plan` |
| 実装する | implement | タスク実行 | `/specramo:implement` |
| 差を確認する | converge | なし | `/specramo:review` |
| 理解を確認する | なし | なし | `/specramo:explain` |

違いは最後の行、**実装者の理解を確認する工程**です。

## 使い方: PRD から PR まで

| 順 | コマンド | すること |
|---|---|---|
| 1 | `/specramo:init` | 設定ファイルと成果物の置き場所を作る |
| 2 | `/specramo:prd` | 対話で要件を集めて PRD を作る |
| 3 | `/specramo:design` | 受け入れ条件の表で振る舞いを固定した Design Doc を作る |
| 4 | `/specramo:plan` | Design Doc を 1 Phase = 1 PR の作業計画書に分ける |
| 5 | `/specramo:phase-design` | Phase 1 つの実装方法を、既存コードを調べてから決める |
| 6 | `/specramo:explain` | 実装前に Phase の設計を説明する |
| 7 | `/specramo:implement` | Phase を 1 つ実装し、完了条件をコマンドで確認する |
| 8 | `/specramo:review` | 差分を 4 観点で並列にレビューする |
| 9 | `/specramo:explain` | 実装後に差分のコードを説明する |
| - | `/specramo:status` | Phase の進み具合と、この後に実行するコマンドを表示する |

1〜4 は最初に 1 回だけ、5〜9 は Phase ごとに繰り返します。

:::details 表にある文書の意味
- PRD: 何のために何を作るかをまとめた要件の文書
- Design Doc: 完成したときの振る舞いを決める設計書
- 受け入れ条件: 完成と言える条件
- 作業計画書: Design Doc を Phase (= PR) に分けた文書
:::

### ゴールは「レビュー依頼のときに説明できる状態」

:::message alert
レビューを依頼するときには、PR の中身を自分の言葉で説明できる状態になっている。これが理想です。
:::

PR を作る作業そのものは、Claude に頼んでも構いません。
でも、**レビュワーの前に立つ実装者が、中身を説明できること**。
ここだけは譲りたくなかったんです！

## こだわったところ

### 1. 細かい決定ほど後で決める

文書は 3 種類あって、細かい決定ほど着手の直前に決めます。

| 文書 | 決めること | 作るフェーズ |
|---|---|---|
| Design Doc | 何を作れば正解か (見える動き) | 最初に 1 回 |
| 作業計画書 | どの Phase で作るか | Design Doc の後 |
| Phase 詳細設計 | どう作るか (メソッド・SQL・トランザクション) | 各 Phase の着手直前。判断が無い Phase では省く |

既存コードを調べてから決めるので、手戻りがぐっと減りました！

### 2. 文章で頼まず、スクリプトで確認する

AI に「〜を確認してください」と書いても、確認されないことがあるんですよね。
なので、**守ってほしいことは検査スクリプトにしました**。

たとえば `phase-gate`。
論理削除 (`deleted_at`) を追加すると、そのテーブルを読む既存のクエリすべてに条件を足す必要があります。
1 件でも見落とすと、消したはずのデータが管理画面に出てきちゃう。
地味に怖いやつです。

そこで、クエリの件数を設計に書かせて、スクリプトが数えた件数と合わなければ FAIL にしてます。

```text
FAIL  table-readers  users: 節は 3 件、改めて数えると 5 件
```

ちなみに、`phase-gate` は論理削除だけじゃなく、データの意味が変わる変更全般で使えます！

:::message
スクリプトが数えるのは SQL の文字列に含まれる `FROM` と `JOIN` だけです。ORM でクエリを組み立てるリポジトリでは、呼び出し元を別に調べる必要があります。
:::

### 3. 実装の前と後で説明を変える

`/specramo:explain` は、実装前は「どこに何の責務を置くか」、実装後は「どの関数が何を返すか」を説明します。
最後には、理解を確認する質問が 1 つ返ってきます。

レビューで未解決の指摘がある箇所は、正しい前提として説明しません。
間違った説明を信じて PR を作ると困るからです。

### 4. レビューは観点ごとに別の AI で

観点ごとに別のエージェントがレビューします。

| エージェント | 確認すること |
|---|---|
| 設計書との比較 | 作業計画書の範囲と受け入れ条件に沿っているか。対象外のファイルを触っていないか |
| 過去の指摘 | チームの過去のレビュー指摘の傾向と比べる (指摘データがあるときだけ) |
| リポジトリの規約 | リポジトリ独自の規約に沿っているか (規約があるときだけ) |
| 言語の指針 | 使っている言語の開発指針に沿っているか |

4 つを並列で動かし、Critical と Warning が 0 件になってから PR を作ります！

## 導入

対象は、PR が 2 本以上に分かれる大きさの開発です。

Claude Code のセッションで、この 2 つを実行します。

```text
/plugin marketplace add DaichiHoshina/spec-ramo
/plugin install specramo@specramo
```

あとは導入先のリポジトリで `/specramo:init` を実行します。

**これで準備は OK です！**

`examples/overdue-todos` に、PRD から Phase 詳細設計までのサンプルがあります。

## 使ってみてどうだったか

数字では測ってないので、ここからは個人の体感です。

### ✅ 品質が上がった

レビューで初めて見つかる問題が減って、レビューコメントの数そのものが少なくなりました。
付いたコメントにも、コードを読み返さずに返信できるようになりました！

### ✅ 結果として、開発全体が速くなった

工程は 1 つ増えたけど、レビューの往復と手戻りが減ったぶんのほうが大きかったです。

### ✅ 頭の負担が減った

1 回に考える範囲が 1 Phase だけになって、毎日ぐったり疲れ切ることがなくなりました。

これが一番うれしかったです！

## おわりに

意外だったのは、**理解の工程を増やしたほうが速くなった**こと。
まさに急がば回れでした！

今は「ここはなぜこうしたの？」と聞かれても、コードを調べ直さずに返信できます。
そもそも、そう聞かれること自体が減りました。

同じようにモヤモヤしている人がいたら、ぜひ一度試してみてください！
