## AIが書いたPRを、自分で説明できますか

Claude Codeで実装を任せるようになってから、PRを作るまでの時間はかなり短くなりました。一方で、困ることも増えました。

- レビューで「ここはなぜこうしたの？」と聞かれて、自分でも即答できない
- 大きな機能を一気に作らせると、1000行を超えるPRができあがってレビューされない
- 設計書はあるのに、実装が設計書からずれていても気づけない

速く作れるようになった分、「自分が理解しないまま進んでしまう」のがボトルネックになっていました。そこで作ったのが Spec Ramo (スペックラモ) です。

## Spec Ramo とは

仕様を PR 単位の Phase に分け、実装者が理解してから Phase を 1 つずつ進める、spec 駆動開発の Claude Code プラグインです。

名前は spec (仕様) + ramo (スペイン語・イタリア語で「枝」) から来ています。1 つの仕様から、Phase ごとの PR へ枝分かれしていくイメージです。

ポイントは3つです。

| ポイント | 中身 |
|---|---|
| 1 Phase = 1 PR | 作業計画書を PR 単位に分け、1 PR で想定する変更の行数が上限 (初期値 400 行) を超えないかを script で検査する |
| 理解してから進む | 実装の前後で `/specramo:explain` が設計とコードを説明し、説明の末尾で理解を確かめる質問を 1 つ返す |
| 観点別の並列レビュー | 設計書との比較 / 過去の指摘 / repo の規約 / 言語の指針、の 4 観点を別々のエージェントで並列にレビューする |

## 使い方: PRD から PR まで

コマンドは次の順に使います。

| 順 | コマンド | すること |
|---|---|---|
| 1 | `/specramo:init` | 設定ファイルと成果物の置き場所を作る |
| 2 | `/specramo:prd` | 対話で要件を集めて PRD を作る |
| 3 | `/specramo:design` | 受け入れ条件の表で振る舞いを固定した Design Doc を作る |
| 4 | `/specramo:plan` | Design Doc を 1 Phase = 1 PR の作業計画書に分ける |
| 5 | `/specramo:phase-design` | Phase 1 つの実装方法を、既存コードを調べてから決める |
| 6 | `/specramo:explain` | 実装前に Phase の設計を説明する |
| 7 | `/specramo:implement` | Phase を 1 つ実装し、完了条件をコマンドで確かめる |
| 8 | `/specramo:review` | 差分を 4 観点で並列にレビューする |
| 9 | `/specramo:explain` | 実装後に差分のコードを説明する |
| - | `/specramo:status` | Phase の進み具合と、この後に実行するコマンドを表示する |

5〜9 を Phase ごとに繰り返します。

**PR は自分で作ります。** Spec Ramo は PR を作りません。9 の説明を読んで「自分の言葉で説明できる」と思えたら、自分の手で PR を作る。この一手を人間の担当にしたのが一番のこだわりです。

## こだわったところ

### 1. 文章で頼まず、script で確かめる

AI に「〜を確認してください」と書いても、確認されないことがあります。そこで、守ってほしいことはなるべく検査 script にしました。

たとえば論理削除 (`deleted_at`) を追加する Phase では、その table を読んでいる query を全部洗い出す必要があります。1 件でも見落とすと、管理画面などで消したはずのデータが表示されてしまいます。Phase 詳細設計に「table を読む query は合計 n 件」と書かせ、script が数えた件数と一致しなければ FAIL にしています。

```text
FAIL  table-readers  「table を読む query」の節が無い (scripts/table-readers.sh の出力を貼る)
```

「調べました」という文章ではなく、件数の一致で調べたことを確かめる、という考え方です。

### 2. 説明は「時点」で分ける

`/specramo:explain` は、同じコマンドでも実装前と実装後で説明する中身が変わります。

- 実装前: どの層にどの責務を置くか、なぜその設計にしたか、処理がどの順序で進むか。コードの逐行説明はしない
- 実装後: どの関数が何を受け取り何を返すか、テストが何を保証するか

レビューで未解決の指摘がある箇所は、「正しい前提」として説明しないようにしています。失敗すると分かっている SQL を「これで完了します」と説明されると、理解したつもりで間違った PR を作ってしまうからです。

### 3. 進捗は作業計画書の表に記録する

各 Phase の状態 (未着手 / 実装中 / レビュー済み / PR 作成済み) は作業計画書の表に記録され、`/specramo:status` で一覧できます。session をまたいでも、この後に何をすればいいかがすぐ分かります。

## 使いどころと使わないところ

言語やアーキテクチャは問いません。Web API / CLI / ライブラリ / バッチ / フロントエンドのどれでも使えます。言語別の指針は今のところ Go と TypeScript を同梱しています。

一方で、**PR が 2 本以上になる規模の作業向け** です。typo や 1 ファイルの小さな修正なら、PRD から始めずにそのまま実装する方が速いです。

## 導入

Claude Code の session で次の 2 つを実行します。

```text
/plugin marketplace add DaichiHoshina/spec-ramo
/plugin install specramo@specramo
```

インストールしたら、導入先の repo で `/specramo:init` を実行します。

## まとめ

- AI で速く作れるようになった分、ボトルネックは「自分が理解しているか」に移った

- 守ってほしいことは文章でなく script で検査する
