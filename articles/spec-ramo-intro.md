## AI が書いた PR を、自分で説明できますか

> 「ここはなぜこうしたの？」

レビューでこう聞かれて、**自分の PR なのに即答できなかった**ことがあります。

コードを生成したのは AI。正直に言うと、自分の理解は浅いままでした。
毎回コードを読んで確かめてから、ようやく返信してたんですよね。

舞台は巨大なモノリスのプロジェクトです。
AI に任せて実装そのものはめちゃくちゃ速くなったのに、レビューや手戻りまで含めると、開発はかえって遅くなってました。品質も低いまま。
毎日頭がぐったり疲れて、体調まで悪くなってました。

これはさすがにまずい、と。

そこで、チーム向けに組み立てた spec 駆動開発の手順を、Claude Code のプラグインにまとめました。
それが Spec Ramo (スペックラモ) です。

## Spec Ramo とは

:::message
仕様を PR 単位の Phase に分けて、実装者が理解してから Phase を 1 つずつ進める、spec 駆動開発の Claude Code プラグインです。
:::

名前は spec (仕様) + ramo (スペイン語・イタリア語で「枝」) から。1 つの仕様から、Phase ごとの PR へ枝分かれしていくイメージです。

チームで困っていたことと、Spec Ramo での対応はこうです。

| 困りごと | Spec Ramo での対応 |
|---|---|
| PR が大きく、読むのに時間がかかる | 1 Phase = 1 PR にし、変更の上限 400 行 (テスト除く) を script で検査する。チームでは目安を 200 行にしている |
| 仕様で決めていなかった点に、実装やレビューで気づく | 実装の前に Design Doc で、見える動きを受け入れ条件の表に固定する |
| 実装者より先に、レビュワーが問題に気づく | 実装の前後に `/specramo:explain` で説明を読み、自分の言葉で説明できてから進む |
| 差分だけでは仕様を読み取れず、レビューが重い | 規約や命名の指摘は、レビュー依頼の前に AI レビューで 0 件にする |

一番つらかったのは 3 行目、冒頭の場面です。速く作れるようになったぶん、**「自分が理解しないまま進んでしまう」こと**がボトルネックになってました。

## 一般的な spec 駆動開発との違い

spec 駆動開発は、コードより先に仕様を決めて、仕様を正として実装する手法です。代表例は GitHub の Spec Kit と AWS の Kiro ですね。

| 工程 | Spec Kit | Kiro | Spec Ramo |
|---|---|---|---|
| 要件を決める | specify | requirements | `/specramo:prd`・`/specramo:design` |
| 設計する | plan | design | `/specramo:design`・`/specramo:phase-design` |
| 作業に分ける | tasks | tasks | `/specramo:plan` |
| 実装する | implement | タスク実行 | `/specramo:implement` |
| 差を確かめる | converge | なし | `/specramo:review` |
| 理解を確かめる | なし | なし | `/specramo:explain` |

注目してほしいのは一番下の行です。
仕様と実装が合っているかを確かめる仕組みは既存の手法にもあります。Spec Ramo はそこに、**実装者の理解を確かめる工程**を加えました。

## 使い方: PRD から PR まで

| 順 | コマンド | すること |
|---|---|---|
| 1 | `/specramo:init` | 設定ファイルと成果物の置き場所を作る |
| 2 | `/specramo:prd` | 対話で要件を集めて PRD を作る |
| 3 | `/specramo:design` | 受け入れ条件の表で振る舞いを固定した Design Doc を作る |
| 4 | `/specramo:plan` | Design Doc を 1 Phase = 1 PR の作業計画書に分ける |
| 5 | `/specramo:phase-design` | Phase 1 つの実装方法を、既存コードを調べてから決める |
| 6 | `/specramo:explain` | 実装前に Phase の設計を説明する |
| 7 | `/specramo:implement` | Phase を 1 つ実装し、作業が終わったかをコマンドで確かめる |
| 8 | `/specramo:review` | 差分を 4 観点で並列にレビューする |
| 9 | `/specramo:explain` | 実装後に差分のコードを説明する |
| - | `/specramo:status` | Phase の進み具合と、この後に実行するコマンドを表示する |

1〜4 は最初に 1 回だけ、5〜9 は Phase ごとに繰り返します。

:::details 表にある文書の意味
- PRD: 何のために何を作るかをまとめた要件の文書
- Design Doc: 完成したときの振る舞いを決める設計書
- 受け入れ条件: 完成したと判定する条件。「〜のとき、〜が〜になる」の形で書く
- 作業計画書: Design Doc を Phase (= PR) に分け、Phase ごとの対象と、作業が終わったと判定する条件を並べた文書
:::

### ゴールは「レビュー依頼のときに説明できる状態」

ここが一番のこだわりです。

:::message alert
レビューを依頼するときには、PR の中身を自分の言葉で説明できる状態になっている。これが理想です。
:::

5〜9 の手順は、全部この状態に向かうためのものです。
9 の説明を読んで「これなら聞かれても答えられる」と思えたら、PR を作ってレビューを依頼します。PR を作る作業そのものは、Claude に頼んでも構いません。

AI に全部やらせることもできます。でも、**レビュワーの前に立つ実装者が、中身を説明できること**。ここだけは譲りたくなかったんです。

## こだわったところ

### 1. 細かい決定ほど後で決める

文書は 3 種類あって、細かい決定ほど着手の直前に決めます。

| 文書 | 決めること | 作るフェーズ |
|---|---|---|
| Design Doc | 何を作れば正解か (見える動き) | 最初に 1 回 |
| 作業計画書 | どの Phase で作るか | Design Doc の後 |
| Phase 詳細設計 | どう作るか (メソッド・SQL・トランザクション) | 各 Phase の着手直前。判断が無い Phase では省く |

着手する Phase の実装方法だけ読めば済むし、既存コードを調べてから決めるので手戻りもぐっと減りました。

### 2. 文章で頼まず、script で確かめる

AI に「〜を確認してください」と書いても、確認されないことがあるんですよね。これ、何度も経験しました。

なので、**守ってほしいことはなるべく検査 script にしました**。
文書ごとに検査があり、FAIL が 0 件になるまで AI が文書を書き換えます。人が読むのはその後です。

たとえば `phase-gate`。
論理削除 (`deleted_at`) を追加すると、その table を読む既存の query すべてに条件の追加が必要です。1 件でも見落とすと、消したはずのデータが管理画面に表示されてしまう。地味に怖いやつです。

そこで、Phase 詳細設計に「table を読む query は合計 n 件」と記載させて、script が数えた件数と合わなければ FAIL にしてます。

```text
FAIL  table-readers  users: 節は 3 件、改めて数えると 5 件
```

「調べました」という文章を信じるんじゃなくて、件数が合うかで確かめる。そういう考え方です。

:::message
script が数えるのは SQL の文字列に含まれる `FROM` と `JOIN` だけです。ORM で query を組み立てる repo では、呼び出し元を別に調べる必要があります。
:::

### 3. 説明はフェーズで分ける

`/specramo:explain` は、実装前と実装後で説明する中身が変わります。

- 実装前: どの層にどの責務を置くか、なぜその設計にしたか、処理がどの順序で進むか
- 実装後: どの関数が何を受け取り何を返すか、テストが何を保証するか

説明の最後には、理解を確かめる質問が 1 つ返ってきます。

レビューで未解決の指摘がある箇所は、「正しい前提」として説明しません。失敗すると分かっている SQL を「正しく更新できます」と説明されたら、理解したつもりで間違った PR を作っちゃいますからね。

### 4. レビューは観点ごとに別の AI で

`/specramo:review` は、観点ごとに別のエージェントを並列で起動します。

| エージェント | 確認すること |
|---|---|
| 設計書との比較 | 作業計画書の範囲と受け入れ条件に沿っているか。対象外のファイルを変更していないか |
| 過去の指摘 | チームの過去のレビュー指摘の傾向と比べる (指摘データがあるときだけ) |
| repo の規約 | repo 独自の規約に沿っているか (規約があるときだけ) |
| 言語の指針 | 使っている言語の開発指針に沿っているか |

Critical と Warning が 0 件になってから PR を作るので、チーム固有の指摘も人のレビューの前に見つけられます。

## 導入

対象は、PR が 2 本以上に分かれる大きさの開発です。言語やアーキテクチャは問いません (同梱の言語指針は Go と TypeScript)。

Claude Code の session で、この 2 つを実行します。

```text
/plugin marketplace add DaichiHoshina/spec-ramo
/plugin install specramo@specramo
```

scope (user / project) を決めてインストールしたら、導入先の repo で `/specramo:init` を実行します。

## 使ってみてどうだったか

数字では測ってないので、ここからは個人の体感です。

### 品質が上がった

理解してから PR を作るので、レビューで初めて見つかる問題が減りました。
レビューコメントの数そのものが少なくなって、付いたコメントにもコードを読み返さずに返信できるようになりました。

### 結果として、開発全体が速くなった

工程は 1 つ増えました。でも、レビューの往復と手戻りが減ったぶんのほうがずっと大きかったです。

### 頭の負担が減った

1 回に考える範囲が 1 Phase だけになって、前みたいに毎日ぐったり疲れ切ることがなくなりました。

正直、これが一番うれしかったです。

## おわりに

意外だったのは、**理解の工程を増やしたほうが速くなった**こと。まさに急がば回れでした。

今は、レビューで「ここはなぜこうしたの？」と聞かれても、コードを調べ直さずに返信できます。
そもそも、そう聞かれること自体が減りました。

AI に任せる範囲が広がるほど、こう答えられる状態を保つ仕組みが大事になると思ってます。

同じようにモヤモヤしている人がいたら、ぜひ一度試してみてください！
